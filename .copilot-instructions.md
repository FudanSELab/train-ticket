## How to Help

### When Analyzing Issues

- Check docs/session_relay.md for current progress and blockers
- Check task description for what phase we're in
- Look at Dockerfiles - they should all start with FROM openjdk:11-jre-slim currently
- Remember: All 41 services need consistent changes

### When Suggesting Code Changes

- Dockerfiles: All need the same base image update
- pom.xml files: Already updated, don't revert Java version
- docker-compose.yml: Infrastructure versions pinned (Redis 7, MongoDB 6.0, MySQL 8.0)
- bash scripts: May need line ending fixes for WSL

### When Proposing Solutions

- Prefer: Using established, maintained images (eclipse-temurin, official MySQL, official MongoDB)
- Avoid: Using latest/unversioned images (need reproducibility)
- Consider: WSL compatibility (bash scripts need Unix line endings)
- Test: Verify changes work locally on Windows WSL first

## Common Patterns

### Bulk File Updates

When updating all 41 services, use multi_replace_string_in_file to apply changes simultaneously:
For each service: ts-*/Dockerfile, ts-*/pom.xml, etc.

### WSL Considerations

- Scripts have CRLF line endings from Windows
- Need to convert to LF for bash in WSL: sed -i 's/\r$//' *.sh
- Paths use forward slashes in bash, backslashes in PowerShell

### Docker Image Naming Convention

hdali00/ts-<service-name>:train-ticket
Example: hdali00/ts-auth-service:train-ticket

## Using the Agent System Efficiently

### The Orchestration Approach

You have ONE master orchestration agent that routes to 3 specialists. This eliminates manual skill selection:

**BEFORE** (Manual skill selection):
```
Copilot, using developer skill, bulk update all services base image to eclipse-temurin:11-jre-alpine
Copilot, using analyst skill, verify build status
Copilot, using reviewer skill, session checkpoint
```

**AFTER** (Natural language routing):
```
Update all service base images to eclipse-temurin:11-jre-alpine
Verify the build
Session checkpoint
```

### When Each Agent Activates

| You Say | Agent Routes To | Why |
|---|---|---|
| "Is the build working?" | ANALYST | Status check → Verification |
| "Fix the docker error" | DEVELOPER | Problem solving → Implementation |
| "Test the deployment" | ANALYST | Validation → Verification |
| "Update all Dockerfiles" | DEVELOPER | Bulk change → Implementation |
| "Document this session" | REVIEWER | Progress tracking → Documentation |
| "Prepare for kubernetes" | REVIEWER + ANALYST | Multi-step → Chains agents |

### Complex Workflows (Agent Chaining)

When you ask for multi-step work, the orchestrator chains agents:

Request: "Complete the docker stage"
```
1. [ANALYST] Verify build status
2. [DEVELOPER] Build docker images
3. [ANALYST] Test docker deployment
4. [DEVELOPER] Fix any issues found
5. [ANALYST] Verify everything working
6. [REVIEWER] Check quality gates
7. [REVIEWER] Prepare relay to kubernetes
```

Request: "Fix the deprecated base image"
```
1. [ANALYST] Investigate current state
2. [DEVELOPER] Update all Dockerfiles to eclipse-temurin:11-jre-alpine
3. [ANALYST] Verify docker build succeeds
4. [REVIEWER] Document the change and rationale
```

### Quick Efficiency Tips

1. **Be specific about context**: "Update all Dockerfiles to eclipse-temurin:11-jre-alpine" (not just "fix docker")
2. **Describe goals, not steps**: "Make the build work" (not "run maven, then docker build")
3. **Use stage names**: "Test deployment for docker stage" (not vague "test it")
4. **End sessions clearly**: "Session checkpoint" (triggers documentation and handoff)
